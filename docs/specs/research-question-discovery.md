# Spec: evidence-backed AI/ML research question discovery

## Problem Statement

A first-paper AI/ML researcher can search for papers but struggles to determine which unanswered question is credible, useful, and feasible with their experience, time, data, and compute. Search results and chat answers rarely preserve the search boundaries, closest prior work, contradictory evidence, and reasoning needed to defend a proposed contribution. Unsupported novelty claims can send the researcher into work that has already been done.

The immediate problem is reaching an inspectable, reviewed Research Question. This spec implements that first vertical slice of the larger research workspace. Research planning, actual experiment records, findings, manuscripts, and submission preparation follow in later specifications.

## Solution

Provide a web-first private workspace that guides an individual researcher from a research brief through a Literature Scope, a dated Literature Snapshot, inspected Evidence Anchors, a small Candidate Gap shortlist, a Gap Review, and an explicitly adopted Research Question. Every proposed literature claim remains attached to its evidence and search limitations. Researcher edits, exclusions, reviews, and revisions survive independently of model calls or chat history.

The initial supported evaluation track is empirical predictive ML, starting with tabular classification. Other AI/ML topics may be explored, with an explicit indication that they are outside the validated track. The product assesses candidate opportunities within a declared search; it does not certify novelty or predict publication acceptance.

The slice is complete when a researcher can sign in, create a project, run and inspect a bounded search, add permitted source text, obtain or manually author an evidence-backed candidate, inspect closest and contrary work, and adopt a question with its rationale and provenance. It must also handle empty results, incomplete sources, insufficient evidence, cancellation, and recovery without fabricating progress.

## User Stories

1. As a pilot researcher, I want to sign in securely, so that my unpublished research remains private.
2. As a researcher, I want only my projects to appear in my workspace, so that another account cannot inspect my work.
3. As a researcher, I want to create, rename, archive, and delete a Research Project, so that I can manage distinct investigations.
4. As a researcher, I want to describe my topic, experience, time, compute, and contribution interests, so that suggestions fit my practical constraints.
5. As a researcher, I want to save an incomplete brief, so that I can return without losing work.
6. As a researcher, I want to see whether my topic is in the validated evaluation track, so that I understand the support available.
7. As a researcher, I want to inspect and edit proposed search queries before running them, so that the literature boundaries reflect my intent.
8. As a researcher, I want to choose dates, sources, and inclusion criteria, so that the literature search is documented and repeatable where provider capabilities permit.
9. As a researcher, I want relevant older work to be considered explicitly, so that a recent date window does not hide foundational research.
10. As a researcher, I want to see what each source actually searched, so that unsupported filters or failed queries are visible.
11. As a researcher, I want a search to continue after I leave the page, so that long operations do not depend on an open browser.
12. As a researcher, I want to see progress, cancel work, and resume from persisted results, so that interruptions do not force a fresh search.
13. As a researcher, I want empty results explained, so that I can revise a query without mistaking emptiness for novelty.
14. As a researcher, I want outages, cached results, and truncation labelled, so that partial coverage is not presented as a complete search.
15. As a researcher, I want duplicate records reconciled without losing versions, so that preprints and published papers remain distinguishable.
16. As a researcher, I want to inspect paper identifiers, source links, dates, and publication status, so that I can assess provenance.
17. As a researcher, I want to include or exclude a paper with a reason, so that my screening decisions are preserved.
18. As a researcher, I want to search and filter my literature library, so that I can find relevant evidence efficiently.
19. As a researcher, I want metadata-only, abstract-backed, and full-text records distinguished, so that I know what the app inspected.
20. As a researcher, I want permitted open documents fetched and my authorized PDFs uploaded privately, so that I can ground research in source text.
21. As a researcher, I want unavailable or unsupported documents explained, so that I can obtain another copy or continue with the stated limitations.
22. As a researcher, I want passages shown with paper version and page or section locators, so that I can check a claim in context.
23. As a researcher, I want to add and correct Evidence Anchors, so that imperfect extraction does not silently become trusted evidence.
24. As a researcher, I want known retractions and withdrawals flagged, so that affected support is reviewed before use.
25. As a researcher, I want a shortlist of at most five supported Candidate Gaps, so that I can compare plausible opportunities without a quota of weak ideas.
26. As a researcher, I want each candidate to state a precise question and potential contribution, so that I can judge whether it matters.
27. As a researcher, I want supporting, contrary, and ambiguous evidence displayed separately, so that disagreement remains visible.
28. As a researcher, I want author-stated limitations distinguished from app inference, so that future-work statements are not treated as proven gaps.
29. As a researcher, I want evidence strength, relevance, and feasibility explained separately, so that a novelty percentage does not conceal uncertainty.
30. As a researcher, I want the closest prior work compared on task, method, conditions, and outcomes, so that superficial differences are not misrepresented as contributions.
31. As a researcher, I want targeted searches for work that could overturn a candidate, so that I can challenge it before committing.
32. As a researcher, I want to inspect and record counter-search outcomes, including unsuccessful searches, so that absence claims retain their limitations.
33. As a researcher, I want to edit, reject, or manually author a candidate, so that model output does not control my research direction.
34. As a researcher, I want insufficient-evidence and invalid-generation states to suggest specific next actions, so that the app does not invent an answer to keep me moving.
35. As a researcher, I want changes to evidence to mark affected reviews as stale, so that I do not adopt a question based on an outdated assessment.
36. As a researcher, I want concurrent edits to report a conflict, so that a background completion or another tab cannot overwrite my review.
37. As a researcher, I want to record significance, feasibility, assumptions, limitations, and my decision in a Gap Review, so that the adopted direction is defensible.
38. As a researcher, I want to acknowledge partial coverage explicitly, so that a usable provisional question can be distinguished from a thoroughly investigated one.
39. As a researcher, I want to adopt a reviewed candidate as my active Research Question, so that the next research stage has a stable starting point.
40. As a researcher, I want earlier question revisions preserved when I change direction, so that I can understand how the investigation evolved.
41. As a researcher, I want to see my next action and missing evidence, so that guidance is tied to my project's actual state.
42. As a researcher, I want model-processing disclosure and generation limits before sending private text, so that I can make an informed choice.
43. As a researcher, I want spending limits and provider failures to preserve my manual workspace, so that unavailable automation does not prevent evidence review.
44. As a researcher using a keyboard or small screen, I want accessible, readable research views, so that I can inspect and edit the evidence without a desktop-only interaction.
45. As a researcher, I want deletion to revoke access immediately and track cleanup, so that late jobs cannot restore private content.
46. As a pilot operator, I want invite control, redacted job diagnostics, and configurable limits, so that I can evaluate the workflow without exposing research text or unbounded spending.

## Implementation Decisions

### Scope, repository baseline, and architecture

1. The repository currently contains planning, research, glossary, and agent instructions. There is no application starter, package manifest, existing test suite, or initial commit. The user supplies the Better T Stack starter; importing and inspecting it is the first implementation prerequisite. Keep the existing planning assets. Do not invent generated package names, versions, or test prior art.
2. Preserve TypeScript, Next.js, Tailwind, web shadcn primitives in the shared UI package, Hono, tRPC, Node.js, Drizzle, PostgreSQL, Better Auth, Biome, and Turborepo. Expo/React Native remains future work. Share API contracts and applicable domain rules with future native clients; DOM components remain web-specific.
3. Next.js owns the web interface. One Node Hono backend owns Better Auth endpoints, tRPC, authorized file operations, and application workflows. Avoid a second business API in Next.js. Put literature access, research decisions, durable job coordination, model calls, and storage behind cohesive application services. Prefer the starter's compatible existing boundaries over creating a package for each entity.
4. Use a separate persistent Node worker from the same codebase, pg-boss with PostgreSQL for durable jobs, private Amazon S3 behind a storage interface, PDF.js for initial text-PDF extraction, PostgreSQL full-text search, and the selected OpenAI Responses adapter for generation. Implement only the capabilities needed by this slice. Do not introduce Redis, vector search, microservices, or native UI.
5. Configure provider credentials, deployment/runtime settings, model ID, current price table, and budget ceilings server-side. Exact versions and hosting vendors are selected during starter reconciliation. Missing live configuration disables the affected automation with a precise status; manual project and evidence operations remain available. Deterministic fixtures support implementation without live credentials.

### Accounts, ownership, and project brief

6. Pilot access is invite-only. Use Better Auth email/password sessions with verified email and an operator-maintained invited-email allowlist; no invite management interface is required. Prefer the starter's existing equivalent flow if present. A production pilot requires working verification/recovery delivery; fixture accounts are for local automated tests only. Every application endpoint resolves session and ownership on the backend. The operator uses an authenticated configuration/administrative process to add or revoke allowlist entries, with actor, time, normalized email, and reason recorded in a private audit trail; no public endpoint can alter eligibility. A revocation denies new research operations and cancels that account's pending research jobs without deleting its projects. Document verification/recovery delivery, invite management, and revocation in an operator runbook before pilot enablement.
7. Projects have one owner. Project-scoped paper selections, files, anchors, reviews, jobs, and generations are private. Public bibliographic facts may be deduplicated across projects internally, but users cannot enumerate another project's existence, selections, private text, or source URLs. Unknown and unauthorized project resources return the same not-found response. An expired or absent session returns an authentication error.
8. A project brief stores title, topic, experience level, time availability, compute description, and desired contribution as editable fields. Title and topic are required to start discovery; other fields may be unknown and then feasibility must state the assumption. Saving an incomplete brief is allowed. Initial bounds are 120 characters for title, 2,000 for topic, and 10,000 total for the brief; validation errors preserve input. No default implies access to a GPU or licensed dataset.
9. A project can be active, archived, or deleting. Archiving makes it read-only and cancels new work until unarchived. Brief changes produce a revision; work records retain the brief revision that informed them. The active Research Question can be absent. Completion guidance is derived from saved artifacts, not one irreversible linear stage flag.

### Literature search and immutable provenance

10. A Literature Scope stores explicit query strings, enabled sources, date range, inclusion/exclusion criteria, and foundation-search intent. The default discovery window is the previous five years through the current UTC date. Citation expansion and direct lookups can add older work, labelled with the acquisition reason. Expose every effective query/filter per source; never silently promise identical source capabilities.
11. Default discovery uses OpenAlex, Crossref for identifier and known status reconciliation, and direct arXiv metadata for recent preprints. Semantic Scholar stays disabled pending applicable product-use permission. Search accepts one to three researcher-editable queries, up to 2,000 characters each. Initial query proposals use deterministic templates derived from the brief; they do not require a paid model call.
12. Each search creates a new immutable Literature Snapshot with scope and brief revisions, timestamps, source outcomes, effective queries, source cursors, cached-data age, returned counts, and coverage limits. An API response's result count is not the number of papers actually inspected. Preserve success, empty, partial, and failed source outcomes separately. A wholly failed search does not create an apparently successful empty corpus.
13. Cap a discovery run at 200 bibliographic records across enabled sources, allowing a deduplicated count below that number. Reserve capacity for arXiv and citation expansion rather than letting one provider consume the entire cap. Persist the actual allocations and truncation. Further searches create explicit snapshots; they do not silently extend a completed snapshot or claim exhaustiveness.
14. Normalize DOI and arXiv identifiers and retain provider aliases. Identified copies and versions stay linked to the scholarly work. Title/author/year similarity produces possible matches, not irreversible merges. Ambiguous matches remain separate pending researcher review. Preserve provenance and document version when a preprint later gains a DOI.
15. Snapshot membership stores included, excluded, or undecided screening status with append-only revisions and reasons. Exclusion requires a reason. Unknown membership starts undecided and cannot support generated gap claims until included. Provider metadata corrections do not silently alter a historical snapshot; a refresh records a new observed version and flags affected use.
16. A project library supports paginated listing, text search, and filters for screening status, year, provider, evidence availability, and known publication status. Known retracted or withdrawn work is visible but cannot be counted as ordinary positive support. It may be discussed as a disputed/historical source with an explicit label. Corrections require review of affected anchors; absent status metadata is displayed as unknown, not clearance.

### Source documents and anchors

17. Source Documents record acquisition route, permitted-use status and basis, external identifiers/version, content checksum, extraction version, and availability. A verified permitted open copy or an authorized private upload can be processed. Unknown permissions produce a metadata/source-link record, not an automatic download. Retain permitted abstract content only under that source's applicable terms. A user upload attestation and explicit external-model-processing consent are distinct actions.
18. API-issued uploads use project-owned unique private keys and short-lived signed access. Verify the actual stored object size, PDF signature/type, checksum, and ownership before parsing. Reject oversized or non-PDF content; client declarations alone are insufficient. Signed uploads/downloads expire within five minutes. Abandoned uploads are cleaned within 24 hours. No public bucket or public document sharing is included.
19. Initial limits are 30 MB and 100 pages per PDF and 20 processed full-text documents per discovery/generation run. Show which papers were selected for processing and allow researcher choice before exceeding the cap. Oversized papers remain usable as metadata or source links. Scanned/low-text or garbled extraction becomes needs-review; OCR is deferred. Do not interpret layout-damaged tables as validated evidence.
20. PDF.js extraction retains page boundaries and text-span locators. Abstract anchors retain their provider/version and a text-span locator instead of a fictitious page. Every Evidence Anchor includes source version, excerpt, locator, context, evidence level, extraction state, and verification history. The reader shows a source link, the accessible document when permitted, and neighboring text. An anchor means a traceable passage, not that its interpretation is scientifically correct.
21. Researchers can create or correct anchors from a source available to their project. User corrections create a revision and preserve the original extraction. Validate corrected excerpts/locators against the source; unmatched text is an unverified user note and cannot become a supporting anchor until resolved. Notes remain private and are not mislabeled as source quotations.
22. Fetching is restricted to configured HTTPS source hosts with redirect and private-network protections. PDFs are untrusted data; parser resource limits and timeouts apply. Embedded document instructions cannot change model/tool permissions. No model output can execute code or initiate arbitrary URL fetches.

### Candidate generation and evidence contracts

23. A generation request references one saved snapshot, its screening revision, included sources, selected anchor revisions, and the brief revision. Freeze and hash this input footprint. Store provider/model identity, prompt/schema version, start/end times, usage, validation outcome, and proposal lineage. Accepted edits are never overwritten by a regenerated proposal.
24. Generate zero to five Candidate Gaps. Each has a proposed Research Question; gap type; scope; significance; potential contribution; relevance, evidence strength, and feasibility with reasons; supporting/contrary/ambiguous claim-to-anchor links; closest prior work; assumptions; coverage limitations; and a concrete next validation step. Gap types cover coverage, comparison, measurement, robustness/generalization, method, conflicting evidence, reproducibility, and feasibility, with an other option. Do not attach a novelty probability.
25. Model outputs reference only known project paper and anchor identifiers, using schema-constrained responses. For each literature-derived factual claim, require a relevant anchor reference; validate project access, source version, evidence level, quotation identity where present, and absence of invalid positive support. An abstract cannot support an invented methods-level comparison. Bibliographic facts come from saved metadata, not generated references.
26. Structural/reference validation does not establish semantic entailment. Display generated candidates as unreviewed proposals. The researcher inspects whether anchors support each important claim before a Gap Review can accept it. Unsupported claims can be removed or revised; they cannot be promoted merely because the output parses. Author-stated limitations, searched-set absence, and app inference are distinct evidence labels.
27. Insufficient evidence returns an explicit needs-evidence artifact with missing information and next actions; generation can legitimately return no candidates. Invalid JSON/schema, nonexistent IDs, or unavailable anchors produce a failed validation outcome and no publishable candidate. Do not silently repair with invented citations or automatically spend on a corrective model call. A manual candidate follows the same evidence/review contract and requires no model budget.
28. Feasibility explanations consider the brief's known time/experience/compute constraints and unknown data access. They are estimates, not verified dataset availability or compute benchmarks. Store feasibility as constraint-checked, provisional, or infeasible. Unknown critical resources permit only provisional feasibility, with each limiting resource, assumption, and a concrete validation/mitigation step named. Known unavailable indispensable data/compute/time makes the candidate infeasible unless the researcher records a credible alternative; acknowledgement alone cannot relabel it feasible. The draft question can propose how to investigate the issue, but this slice does not generate or claim an approved Research Plan.

### Gap Review, counter-search, adoption, and staleness

29. The comparison view defaults to the three closest relevant works found in the declared corpus. Each comparison states task, method, conditions, claimed result, overlap, and possible distinction, with evidence levels and anchors for factual content. Fewer than three is allowed with a visible coverage limitation; missing comparisons must never be fabricated. The researcher can replace a suggested closest work and records the rationale.
30. A counter-search is an explicit new search run, retaining its own scope, snapshot, coverage, and budget accounting. Seed one to three editable queries from the candidate's concepts, synonyms, and closest-work terminology. New evidence can be attached to a candidate revision; the original snapshot remains intact. At least one completed counter-search attempt is required to finish a Gap Review. Failed/partial attempts remain visible and require explicit limitation acknowledgement.
31. A Gap Review references the exact candidate revision, base snapshot/screening revision, supplemental snapshots, selected closest-work comparisons, and verified anchor revisions. Required fields are significance, feasibility rationale, assumptions, limitations, important-claim verification decisions, counter-search assessment, and a decision of accept, revise, or reject. The review explicitly resolves or bounds critical resource uncertainties and cannot accept an infeasible candidate without revising it. A provisional question may be accepted with named checks still outstanding; the review and adopted question retain that label rather than implying confirmed feasibility. Contrary evidence is addressed explicitly. The reviewer is the project owner; no collaboration role is implied.
32. Accepting a review requires every important factual claim to have inspected support or to be removed/reclassified as an explicit hypothesis, and all included contrary evidence to have a recorded assessment. Structural defects and invalid positive support block acceptance. Partial coverage alone need not block a provisional question: require an acknowledgement that names the failed, limited, or stale source. A failed counter-search cannot establish absence of prior work.
33. Adoption creates an immutable Research Question revision linked to an accepted, non-stale Gap Review. Store question text, scope, intended contribution, rationale, unresolved limitations, and reviewed evidence footprint. Exactly one revision is current per project; previous revisions remain inspectable. The title/action says adopt question, never certify novelty. Hypotheses remain intentions, not Findings.
34. Snapshot replacement, changed screening, edited source/anchor content, candidate revision, changed constraints, or a relevant publication-status update flags affected reviews and current questions for revalidation. Preserve prior artifacts and show the reason. A new supplemental search makes a review stale only when attached to or promoted for that investigation; merely running an unrelated search does not alter an adopted question. No background update silently re-adopts or deletes a question.
35. Stale artifacts can be read and edited, but cannot support a fresh adoption until reviewed against the new footprint. Changing the current question creates a new revision. Rejecting a candidate does not erase its rationale or evidence. Adoption and saved reviews use optimistic concurrency: submit the expected artifact revision, reject conflicting writes, and let the researcher reload/compare without losing unsaved text.

### API operations and persisted relationships

36. tRPC exposes authenticated workflow operations for project lifecycle/brief revisions; scope validation and search submission; snapshot/source outcomes and library screening; source/anchor reading and correction; generation submission; candidate editing/comparison; counter-search attachment; review saving; question adoption/history; job progress/cancellation; and budget availability. Upload preparation/completion and authorized download issuance are Hono HTTP operations. Responses are paginated and include stable IDs and revision/version information; do not return private text in generic job lists.
37. Search, parsing, and generation submissions validate project ownership, bounds, expected input revision, consent/rights where applicable, active-job limits, and metered budget before queueing. Accepted submissions return a job ID and saved input footprint immediately. Duplicate submissions with the same project/action/idempotency key and input return the existing operation; reuse with different input is a conflict. Reads and review/adoption decisions are synchronous.
38. Domain errors distinguish invalid input, revision conflict, source unavailable, permission unknown, extraction needs review, insufficient evidence, generation validation failure, budget exceeded, and job cancelled. The UI offers a relevant next action without exposing raw upstream errors, secrets, or another user's resource existence. Completed partial-source runs return their individual outcomes, not a generic successful-coverage flag.
39. Persist project/brief revisions, Literature Scopes/Snapshots and source executions, snapshot membership and screening revisions, canonical Paper identifiers/aliases and version relationships, private Source Documents and extraction revisions, Evidence Anchors/revisions, Candidate Gaps and claim/evidence links, comparisons, Gap Reviews, Research Question revisions, jobs/stage outputs, and usage reservations. Enforce uniqueness for stable identifiers/idempotency keys, project ownership for every private relationship, and one active question per project. Store provenance relationally rather than only inside opaque model JSON.
40. Do not create future plan, experiment, finding, or manuscript tables prematurely. The reviewed question and its immutable evidence footprint are the interface later slices consume. Persist sufficient provenance now to add those relationships without recreating historical searches.

### Job safety, budgets, and deletion

41. Application writes and pg-boss enqueueing share one PostgreSQL transaction. Jobs expose queued, running, succeeded, failed, or cancelled execution states; document and proposal review states are separate. Stages checkpoint persisted results and use stable input/version keys. Worker recovery cannot duplicate saved papers, proposals, or reviews. The browser polls job status at approximately five-second intervals while visible, backs off on errors, and refetches on focus/reconnect; background browser activity is unnecessary.
42. Apply bounded transient retries to safe retrieval stages, at most three total attempts with backoff and provider-directed throttling. Enforce source quotas across all workers, not separately per account. Metered attempts require reserved budget, including retries. Do not claim exactly-once execution of external calls: an ambiguous model-call outcome becomes a visible uncertain/failed operation with held accounting, without automatic paid re-execution. A researcher-requested new attempt has a new reservation and preserves the prior attempt's history.
43. Initial ceilings are two active research runs per account, two executing worker runs globally, and 50,000 aggregate model input tokens per generation run. Output limits are configured and included in price reservation. Per-run variable spend is capped at $1; per-project monthly spend at $5; global monthly spend at $50, using UTC calendar months. Metered literature downloads/search and model calls all count; hosting/storage are outside these variable limits. These are chosen pilot policies, not price estimates or performance guarantees.
44. Before each paid call, reserve its conservative maximum charge atomically against all applicable caps, including concurrent requests and pending reservations. Unknown pricing or unavailable quotas disables that paid route. Reconcile measured usage; release only unused confirmed amounts. Cache reusable results only where permissions allow, keyed by source/input/version. Budget exhaustion stops further paid stages but preserves completed evidence and manual review/adoption. Operators adjust limits through configuration with auditable changes; no billing/upgrade flow is included.
45. Cancellation prevents new stages and rejects late publication of private artifacts; completed checkpoints remain available in an active project. Archive and deletion also cancel pending work. Deletion immediately tombstones the project, denies all further access/signing/publication, and queues cleanup of private text/files/relationships. In-flight responses may still incur charges, recorded without retaining deleted research content.
46. Signed URLs already issued cannot be promised instantly revocable; their five-minute expiry bounds access, and prompt object deletion ends access sooner where supported. Cleanup retries are idempotent and operator-visible; private object/text cleanup completes within 24 hours under healthy dependencies. The deployed backup-expiry policy and external-provider retention are disclosed separately. Do not promise immediate deletion from backups or provider logs. Shared public bibliographic facts may remain after private project relationships are removed.

### Interface and pilot guidance

47. Implement project list, project overview/brief, Literature, Gaps, and Research Question views. Literature has scoped search controls, source-status summary, a readable library, and evidence inspection. Gaps provides side-by-side candidate comparison and focused review with closest/contrary work. The question view shows the current revision and rationale. Future Plan/Experiments/Manuscript views are outside scope; do not show dead navigation.
48. A persistent progress guide derives the next action from saved state: complete brief, review scope, inspect search, obtain evidence, review candidates, counter-search, resolve stale/unsupported claims, or adopt question. Account, source, parsing, evidence, and budget issues have independent visible explanations. Provisional feasibility and outstanding resource checks remain visible on candidates, reviews, and the adopted question. Leaving and reopening a project restores artifacts and job status without requiring a chat transcript.
49. Use a light, readable research interface with strong typographic hierarchy, restrained accent color, and evidence badges alongside the relevant claims. Content drives layout; no novelty gauges or decorative analytics. Support keyboard navigation, labelled forms, visible focus, status announcements, clear error text, contrast, and responsive layouts at 360px and 1280px. Long excerpts and comparisons must remain inspectable without requiring horizontal scrolling of the whole page.
50. Show external-model-processing purpose and content categories before transmitting any private project content, including the brief, source text, researcher notes, and candidate/review inputs; record scoped, versioned consent and permit refusal while retaining manual workflow. Separately, confirming a literature search discloses the exact queries sent to the selected source services. Send no other private brief fields to literature providers. Public metadata alone does not require private-content consent; consent changes invalidate pending calls outside the newly allowed scope. Model configuration uses stateless extracted-text requests under the selected adapter; do not represent this as zero provider retention. Logs contain job/error classes, timing, quota/usage, and anonymous operational counts, not paper excerpts, manuscript text, credentials, or private queries.

## Testing Decisions

1. **Primary seam:** exercise the authenticated API and complete project workflow against real disposable PostgreSQL persistence, the actual job coordinator, and deterministic literature/model/storage boundaries. Assertions concern user-visible saved artifacts, access rules, provenance, coverage, errors, and recovery. Avoid tests that mirror ORM calls, prompt strings, or internal component structure. Use the supplied starter's test runner where suitable; otherwise select Vitest for these integration tests and Playwright for a small browser acceptance suite. There is no existing local test prior art.
2. **Controlled external dependencies:** fixtures return reproducible source outcomes, text extraction samples, known identifiers/versions, model proposals, and measured usage. Fixture content is permitted for testing. Workers run through the same job dispatch/recovery path used in production; a narrow in-process executor may speed ordinary tests, while restart/retry tests use the durable queue. No routine test requires paid APIs.
3. **Acceptance — happy path:** an invited verified account creates a project and brief, reviews scope, runs discovery, includes relevant papers, acquires permitted text, verifies anchors, generates a candidate, completes comparisons and counter-search, accepts a Gap Review, and adopts a question. Reloading and signing back in preserve provenance and the active question. This scenario is covered at the API seam plus one browser journey.
4. **Acceptance — isolation:** a second account cannot list, fetch, change, link, generate from, adopt from, or sign access to the first account's private resources. Include guessed job/document/anchor/review identifiers and cross-project evidence links, not just project-list filtering. Uninvited/unverified and subsequently revoked accounts cannot access pilot research operations. Private-content transmissions require the relevant consent; refusing or withdrawing it prevents calls while manual work remains available.
5. **Acceptance — search truth:** fixtures cover empty success, total failure, one failed source, stale cache, unsupported filter, query truncation, older-foundation expansion, ambiguous duplicates, and preprint/published versions. The saved and visible scope/outcomes remain accurate; no state asserts an exhaustive search or equates emptiness with a gap.
6. **Acceptance — document integrity:** include valid text PDF, abstract-only record, unknown rights, oversize upload, mismatched type/checksum, scan/garbled text, table ambiguity, missing locator, corrected quotation, and malicious embedded instructions. Invalid/low-quality content cannot become trusted support; permitted source snippets remain locatable and versioned. Test private-network/redirect protection with controlled network fixtures.
7. **Acceptance — candidate integrity:** models return supported proposals, fabricated IDs, cross-project anchors, a nonexistent quotation, abstract-level overreach, zero candidates, invalid schema, and a known retracted source used as positive support. Structural invalidity cannot create an adoptable candidate; valid proposals stay unreviewed until claim inspection. Manual authoring uses the same rules.
8. **Acceptance — review/adoption:** exercise fewer than three closest works, an explicit contrary study, successful and partial/failed counter-search, unresolved important claims, absent required rationale, stale anchors, a changed brief, new relevant status, unrelated supplemental search, revision conflicts, and replacement of the active question. Acceptance gates and history behave as specified without erasing user edits. Include unknown constraints yielding a provisional question and known indispensable unavailable resources blocking acceptance until a documented alternative exists.
9. **Acceptance — durability:** enqueue rolls back with its application write; repeated submissions return one operation; a worker restart resumes checkpoints; safe retries remain bounded; cancellation/archive/deletion prevent late publication. Simulate a model response lost after dispatch: budget remains conservatively held and no automatic paid duplicate call occurs.
10. **Acceptance — cost/deletion:** concurrent reservations cannot exceed run/project/global caps; UTC month rollover preserves previous accounting; unknown prices and exhausted provider quotas block only affected paid work. Deletion immediately denies reads and new signed URLs, retries cleanup, and exposes retained-backup/provider boundaries. Already-issued URL lifetime matches the selected expiry policy.
11. **Browser checks:** verify the happy path, empty/partial search, stale review, insufficient evidence, budget stop, and accessible keyboard interaction in readable desktop and small-screen layouts. Use fixture-backed browser runs; do not turn every persistence assertion into a slow browser test.
12. **Live integration gates:** before enabling pilot automation, validate actual source credentials/permissions and response fields, representative licensed PDF extraction/anchors, model schema support and refusal handling, usage pricing/reservation estimates, queue transaction compatibility and deployed worker recovery, private object signing/cleanup, and auth verification/cookie/origin behavior. Exact latency/cost are measured here rather than invented in the spec. Starting any server still requires permission under repository rules.
13. **Scientific quality gate:** evaluate approximately twenty expert-reviewed empirical-ML cases containing closest and contrary work, supported/unsupported gap statements, stale evidence, and constrained feasibility. Preserve raw generated proposals before correction and score both raw and reviewed output separately. Critical errors include fabricated or materially unsupported gap/closest-work claims, concealed decisive counterevidence, and a knowingly infeasible question presented as feasible; the expert records adjudication and the number of cases/candidates/claims assessed. Enabling generated candidates in the pilot requires zero such critical errors in the raw launch set, all seeded indexed closest/contrary works retrievable within the declared scope either found or honestly unavailable with the affected case marked provisional, and zero unresolved critical errors after review. Report missed-work counts, edits per candidate, and median review time; use fifteen minutes per case as a chosen initial usability target, not an advertised performance claim. If the safety gate fails, keep model generation disabled and pilot the manual evidence/review flow until retrieval or generation is corrected and re-evaluated. No claim of general automation reliability follows from this development set; the live pilot additionally evaluates usefulness and repeat use.
14. **Completion:** all automated acceptance scenarios pass; TypeScript and Biome checks pass; migrations and job recovery are demonstrated; the live integration and scientific quality gates are recorded before live pilot enablement, including operator invite/revocation and verification/recovery exercises.
