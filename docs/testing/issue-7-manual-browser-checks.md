# Ticket #7 manual browser checks

These checks are written for the user to run manually, as requested. They have **not** been executed by the implementation agents. Do not infer browser, cookie, or layout verification from passing API integration tests. Starting the local web/API servers requires permission under `AGENTS.md`; no server is started by this checklist or the optional Playwright configuration.

Use a disposable development database and two synthetic accounts, A and B. Keep production accounts/data out of this walkthrough. The application uses the existing auth forms; invitation and verified-email behavior is delivered in ticket #8. For direct local development, configure web `NEXT_PUBLIC_SERVER_URL=http://localhost:3000` and `SERVER_URL=http://localhost:3000`, and server `BETTER_AUTH_URL=http://localhost:3000/api/auth`, `CORS_ORIGIN=http://localhost:3001`, `BETTER_AUTH_SECRET` and the disposable `DATABASE_URL`. Deployed same-origin web uses `/api`; do not copy local origins into deployment. The existing cookie defaults are validated and corrected by ticket #8. If the browser does not retain a local session, record that failure rather than changing cookie security by hand.

Repeat the project journey at **1280px** and **360px** viewport widths. Check long titles, multiline topics, error messages, and revision history at both widths. Pages, form controls and action confirmations must remain readable without horizontal scrolling, and the focused control must remain visible.

1. Signed out, open `/dashboard` and a known `/projects/<id>` URL. Both should redirect to `/login`. Sign in as A. The header should lead to Projects; there should be no starter API-status artwork, demo dashboard navigation, or dead future research views.
2. On Projects, leave Working title blank and create a Research Project. It should open an incomplete saved brief. Add a title but leave the topic/resources blank, then save. A new revision should appear; unknown resources must not imply access to GPUs, data or licensed material. Leave and reopen the project, then reload: the saved fields and revision history should remain.
3. Fill the topic and constraints, save and reload. Rename through Working title and save: both the overview and returned project list should use the new title. Earlier revisions should preserve earlier titles/briefs. The next action should derive from saved title/topic; no search or live pilot should run.
4. Use only Tab, Shift+Tab, Enter and Space for create/save/archive/restore/delete controls. Every input should have an associated visible label. A validation error should be announced and associated with its fields; focus should remain usable. Create/save should not submit twice while pending.
5. Check 120-character title and 2,000-character topic limits. Use resource/contribution text that pushes the combined saved brief beyond 10,000 characters; saving should show a labelled error and preserve all unsaved text. Blank constraints count as the saved word `unknown`. Restore a valid length and save successfully.
6. Open the same project in tabs A1 and A2. Save a changed brief in A1; change a different field in A2 and save. A2 should show the conflict while retaining its own text. Refresh/compare the saved revision using the supplied recovery controls. Loading a saved brief must require an explicit choice before discarding the draft; retaining the draft against the newer revision should allow a deliberate retry. If editing is allowed during save, newly typed text must survive the response; otherwise the editor should be disabled while saving.
7. Make unsaved edits and follow Projects or header navigation, or reload/close the tab. The UI should warn before losing the draft. Cancel should keep the draft. Do not expect drafts discarded by an explicitly confirmed navigation to survive forever.
8. Cancel an archive confirmation and verify the project remains active. Confirm archive: the project should move to Archive, remain readable with history, and reject brief changes/deletion. Restore it and confirm that editing works. Attempt archive while unsaved changes exist: the UI should preserve or explicitly resolve the draft before making it read-only.
9. Cancel a delete confirmation and verify the project remains. Confirm deletion of an active disposable project: return to the list, where it is absent. Reopen its old URL; it should be unavailable. Cleanup can remain pending after access is revoked; backups/provider copies are not claimed erased instantly.
10. In a separate browser profile, sign in as B. B should not see A's projects. Paste A's active, archived and deleted project URLs; the unavailable message should match a well-formed random project UUID. B must not edit, archive, restore, delete, or read revision history for A's project. Test sign-out and a return to the saved list after signing back in as A.
11. If creating enough disposable fixtures to exceed one list/history page, use Load more projects and Load older revisions. Every saved record should remain reachable without repetitions or omissions. Archiving/restoring should refresh the correct list.
12. In the **same browser tab**, open A's list and brief, sign out, then sign in as B. The authentication transition should load a new document; no A title, brief or history should appear, including when B opens A's former URL or the network is slow. Repeat with a save pending when A signs out: its late response must not repopulate B's page. Change the signed-in account in another tab and refocus the project tab; once the new identity is confirmed, its previous private view must disappear and reload for the current account.

Record each check as pass/fail with browser/version, viewport, account profile, and the visible failure. Session-cookie/local-auth issues belong to ticket #8; this ticket must not be described as a live-ready pilot. The optional `apps/web/tests/projects.spec.ts` covers a shorter authenticated keyboard/save/reload/lifecycle journey once fixture browser state and permitted servers are available; it was not run in this batch.
